# Diwali House: working agreement

Diwali House is a production web app for hosting private Diwali parties: an illustrated homepage story, then a party "house" with multiplayer games, a shared jukebox, a collaborative rangoli and a guestbook. Read `docs/architecture.md`, `docs/product-spec.md` and `design/visual-direction.md` before changing anything substantial.

## Non-negotiables

- **Party isolation.** Every read and write of party data goes through `apps/web/src/server/parties/service.ts`. Party-scoped functions take a `MemberContext` (only `authenticate()` makes one) and run inside `withPartyScope()`, so Postgres RLS enforces the party boundary. Never query party tables outside the service, never trust a party or member id from the client without authenticating it, and never filter another party's data out on the frontend.
- **Uniform failure.** Non-member, unknown party, malformed id and revoked session must look identical (401 / "This door is closed").
- **Server-authoritative games.** Game rules run in the pure engines (`packages/teen-patti`, `tambola`, `raja-mantri`, `charades`, sharing `packages/game-kit`) inside the `GameRoom` Durable Object, wired up in `apps/realtime/src/engines.ts`. Clients send intents and render the engine's per-person view only. Never send hidden cards, other players' tickets or chits, the current film, the deck or bag, or RNG seeds to a client. Engines stay pure (no I/O, clock or `Math.random`), and each has a rules document in `docs/games/`.
- **Realtime trusts only tickets.** The Worker acts on identity from a verified ticket; ticket claims come from Postgres via the web app, never from the browser.
- **Virtual chips only.** No real-money mechanics, purchases or cash-out, ever.
- **No fake functionality.** No dead buttons, no pretend success states, no placeholder art in shipped screens. Unbuilt things say so in a designed way.
- **Respectful cultural content.** Follow `design/visual-direction.md` § 8. Never present one account as _the_ meaning of Diwali. Don't draw deities or gurus as decoration.

## Design system rules

- Colours come only from the `@theme` palette in `apps/web/src/styles/globals.css` (Tailwind's defaults are disabled). SVG art imports `PALETTE` from `design-system/palette.ts`. A test keeps the two in sync.
- Text uses the `type-*` role classes. Don't invent ad-hoc font sizes.
- **Never letter-space Indic scripts.** Mark every Devanagari, Gurmukhi or Bengali run with `lang`. Use Tiro, not Rozha, for Devanagari numerals (Rozha draws them as Latin digits).
- No blurred shadows, no glassmorphism, no gradients as decoration, no emoji as illustration, no stock icons. Glow means "live" and is used for nothing else.
- Animate only `transform` and `opacity`. Every animation has a reduced-motion path that is a finished composition, not a broken one. No autoplay audio.
- New artwork needs a row in `design/asset-manifest.md` (source, licence) before it merges. Files in `design/references/` are never shipped.

## Code conventions

- TypeScript strict, with `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`. Optional props that may receive `undefined` are typed `?: T | undefined`.
- Packages (`packages/*`) ship `.ts` source with explicit `.ts` import extensions and `erasableSyntaxOnly`. The web app uses the `@/` alias.
- Runtime validation with Zod at every boundary. Shared schemas live in `@diwali/contracts`.
- Server-only modules import `server-only`. `service.ts` must stay free of Next.js imports so it can be tested directly.
- Styling: Tailwind for layout; CSS Modules plus tokens for the visual identity.
- Comments explain _why_. Keep them at the density of the surrounding code.
- Structured logs via `server/log.ts`. Never log tokens, cookies, IPs or invite codes.
- **Next.js 16 differs from older versions.** Its bundled docs are in `apps/web/node_modules/next/dist/docs/`; check them before relying on remembered APIs. (`apps/web/AGENTS.md` is generated by `next dev`.)

## Testing

- `pnpm test` runs Vitest. Integration tests use a real Postgres (`DATABASE_URL_TEST`, dropped and recreated every run; its name must contain "test").
- `pnpm test:e2e` runs Playwright against a production build on :3100 with its own database.
- Any change to authorisation or isolation needs a test that fails without it.
- Visual QA: `node apps/web/scripts/capture-screens.mjs` (needs the dev server) writes phone and desktop screenshots to `apps/web/test-results/screens/`. Look at them.

## Commands

```
pnpm dev          # web app on :3000 + realtime Worker on :8787
pnpm --filter @diwali/realtime-protocol keys   # local ticket key pair
pnpm --filter @diwali/realtime smoke           # a hand over real sockets
pnpm db:migrate   # apply supabase/migrations to DATABASE_URL
pnpm test         # Vitest, all packages
pnpm test:e2e     # Playwright
pnpm typecheck && pnpm lint
```
